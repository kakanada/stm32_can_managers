# Параметры периферии CAN/FDCAN в CubeMX - полный разбор для can_manager

Этот документ разбирает ПО ОДНОМУ все параметры инициализации периферии (`FDCAN_InitTypeDef` /
`CAN_InitTypeDef` HAL), которые видны на вкладке настройки периферии в CubeMX, и указывает, что с
каждым из них делать, чтобы `can_manager` работал корректно: какие значения **обязательны**, какие
**рекомендованы**, а какие **свободны** (библиотеке безразличны). Краткая версия тех же требований -
в README.md ("Требования к настройке в CubeMX"); здесь - развёрнуто и по каждому полю отдельно, без
пропусков.

Названия параметров даны по полям структуры HAL (`FDCAN_InitTypeDef`/`CAN_InitTypeDef`) - именно так
они и называются в сгенерированном CubeMX коде (`MX_FDCANx_Init()`/`MX_CANx_Init()`); подписи на
самой вкладке CubeMX могут незначительно отличаться по формулировке между версиями, но соответствуют
этим полям 1:1.

## FDCAN (STM32H7, STM32G4, STM32U5 и т.п. - `HAL_FDCAN_MODULE_ENABLED`)

### Формат кадра и режим работы

| Параметр | Допустимый диапазон | Что нужно библиотеке |
|---|---|---|
| `FrameFormat` | Classic CAN / FD без BRS / FD с BRS | **Обязательно Classic CAN** (`FDCAN_FRAME_CLASSIC`). Библиотека работает только с кадрами 0..8 байт без Bit Rate Switching - FD-кадры (до 64 байт) не читает и не пишет (см. "Честные ограничения" в README.md). |
| `Mode` | Normal / Internal LoopBack / External LoopBack / Bus Monitoring / Restricted Operation | **Normal** для реальной работы на шине. LoopBack-режимы можно использовать временно для автономной отладки без железа - библиотека с ними тоже работает (это просто режим приёма/передачи на уровне ядра контроллера), но это не её рабочий режим. |
| `AutoRetransmission` | ENABLE / DISABLE | **Рекомендуется ENABLE.** При `DISABLE` кадр, проигравший арбитраж шины или получивший ошибку, аппаратно отменяется без повтора - `CANMGR_Send()`/`CANMGR_SendLatest()` при этом всё равно вернут `HAL_OK` (отправка в аппаратный буфер прошла успешно), а кадр молча потеряется на шине с несколькими активными узлами. Если `DISABLE` - осознанный выбор (например, нужна отправка без повторов), библиотека не блокирует инициализацию, только пишет предупреждение `LOG_CODE_CANMGR_NO_AUTORETRANS`, если включён логгер (см. API_REFERENCE.md). |
| `TransmitPause` | ENABLE / DISABLE | **Свободно.** Пауза между последовательными передачами одного узла не влияет на корректность работы библиотеки, только на пропускную способность. |
| `ProtocolException` | ENABLE / DISABLE | **Свободно.** Обработка Protocol Exception Handling - аппаратная особенность FDCAN-ядра, библиотека её не использует и не зависит от неё. |

### Битовый тайминг (Nominal/Data)

| Параметр | Допустимый диапазон | Что нужно библиотеке |
|---|---|---|
| `NominalPrescaler` | 1..512 | **Свободно** - подбирается под нужную скорость шины (битрейт), библиотеке конкретное значение безразлично, важен только итоговый результат (битрейт должен совпадать с остальными узлами на шине). |
| `NominalSyncJumpWidth` | 1..128 | **Свободно**, см. выше. |
| `NominalTimeSeg1` | 2..256 | **Свободно**, см. выше. |
| `NominalTimeSeg2` | 2..128 | **Свободно**, см. выше. |
| `DataPrescaler` | 1..32 | **Свободно, фактически не используется.** Поля Data-тайминга относятся к Bit Rate Switching (BRS) в FD-кадрах - при `FrameFormat = Classic CAN` (обязательное требование выше) они не применяются аппаратно. Можно оставить значения CubeMX по умолчанию. |
| `DataSyncJumpWidth` | 1..16 | Аналогично - не используется при Classic CAN. |
| `DataTimeSeg1` | 1..32 | Аналогично - не используется при Classic CAN. |
| `DataTimeSeg2` | 1..16 | Аналогично - не используется при Classic CAN. |

### Message RAM и фильтры

| Параметр | Допустимый диапазон | Что нужно библиотеке |
|---|---|---|
| `MessageRAMOffset` | 0..2560 | **Свободно.** CubeMX обычно считает это автоматически при нескольких FDCAN-инстансах на одном чипе (чтобы области в общей Message RAM не пересекались) - трогать вручную не нужно. |
| `StdFiltersNbr` | 0..128 | **Обязательно >= 1.** Библиотека конфигурирует ровно один широкий Standard-фильтр (`CANMGR_FDCAN_FILTER_INDEX = 0`) - под него нужен минимум один выделенный элемент в Message RAM. С `0` (умолчание CubeMX) `HAL_FDCAN_ConfigFilter()` тихо пишет за пределы невыделенной области и возвращает `HAL_OK` - приём не работает вообще, а `CANMGR_Init()` теперь явно возвращает `NULL` в этом случае (см. API_REFERENCE.md). Значения больше 1 не вредят, просто расходуют Message RAM впустую - библиотеке нужен ровно один. |
| `ExtFiltersNbr` | 0..64 | **Обязательно >= 1.** Та же причина, что и выше, только для Extended-фильтра (библиотека конфигурирует оба типа - Standard и Extended - одним и тем же вызовом `CANMGR_Init()`). |

### Rx FIFO0 / FIFO1 / Rx-буферы

| Параметр | Допустимый диапазон | Что нужно библиотеке |
|---|---|---|
| `RxFifo0ElmtsNbr` | 0..64 | **Обязательно >= 1** (реально нужно больше - это глубина аппаратного буфера приёма между прерываниями; при `0` приём работать не может). Чем выше трафик на шине и чем позже может быть обработано прерывание приёма, тем больше нужно элементов, чтобы не ловить переполнение (`LOG_CODE_CANMGR_RX_OVERFLOW`/`CANMGR_GetRxOverflowCount()`). Разумное начальное значение - 16..32. |
| `RxFifo0ElmtSize` | 8 / 12 / 16 / 20 / 24 / 32 / 48 / 64 байт | **Обязательно 8 bytes data field** (`FDCAN_DATA_BYTES_8`) - больше библиотеке не нужно (Classic CAN, максимум 8 байт полезной нагрузки), меньше HAL не позволяет. |
| `RxFifo1ElmtsNbr` | 0..64 | **Обязательно 0 (или не важно).** Библиотека использует только RxFIFO0 - конфигурирует фильтры с `FDCAN_FILTER_TO_RXFIFO0`, RxFIFO1 не читает никогда. Можно оставить 0, чтобы не расходовать Message RAM, либо использовать независимо для своих целей вне библиотеки - на её работу не влияет. |
| `RxFifo1ElmtSize` | 8..64 байт | **Безразлично** (см. выше - FIFO1 библиотекой не используется). |
| `RxBuffersNbr` | 0..64 | **Обязательно 0 (или не важно).** Библиотека не использует выделенные Rx-буферы (Dedicated Rx Buffers), только RxFIFO0. |
| `RxBufferSize` | 8..64 байт | **Безразлично** (см. выше). |

### Tx FIFO/Queue и Tx-буферы

| Параметр | Допустимый диапазон | Что нужно библиотеке |
|---|---|---|
| `TxEventsNbr` | 0..32 | **Безразлично, можно 0.** Библиотека не читает Tx Event FIFO (`FDCAN_NO_TX_EVENTS` при отправке). |
| `TxBuffersNbr` | 0..32 | **Обязательно 0 (или не важно).** Библиотека отправляет только через `HAL_FDCAN_AddMessageToTxFifoQ()` (Tx FIFO/Queue), выделенные Tx-буферы (Dedicated Tx Buffers) не использует. |
| `TxFifoQueueElmtsNbr` | 0..32 | **Обязательно >= 1** - это аппаратная глубина, в которую `CANMGR_Send()`/канал опустошения очереди кладёт кадры через `HAL_FDCAN_AddMessageToTxFifoQ()`. При `0` отправка невозможна физически (`HAL_FDCAN_GetTxFifoFreeLevel()` всегда вернёт 0, кадры будут копиться в программной очереди библиотеки и никогда не уйдут на шину). Рекомендуется 4..8. |
| `TxFifoQueueMode` | FIFO mode / Queue mode | **Обязательно FIFO mode** (`FDCAN_TX_FIFO_OPERATION`). В Queue mode аппаратура передаёт несколько ожидающих кадров НЕ в порядке постановки, а по приоритету (меньший ID - раньше) - это ломает инвариант библиотеки "новый пакет никогда не обгоняет уже стоящие в очереди" (см. `can_manager.h`), как только в аппаратном буфере одновременно оказывается больше одного кадра. |
| `TxElmtSize` | 8..64 байт | **Обязательно 8 bytes data field** (`FDCAN_DATA_BYTES_8`) - аналогично `RxFifo0ElmtSize`, Classic CAN не использует больше. |

## bxCAN (STM32F0/F1/F2/F3/F4/L4/G0 и т.п. - `HAL_CAN_MODULE_ENABLED`)

### Режим и тайминг

| Параметр | Допустимый диапазон | Что нужно библиотеке |
|---|---|---|
| `Prescaler` | 1..1024 | **Свободно** - подбирается под нужный битрейт, конкретное значение библиотеке безразлично. |
| `Mode` | Normal / LoopBack / Silent / Silent LoopBack | **Normal** для реальной работы на шине (LoopBack/Silent - только для автономной отладки, не рабочий режим). |
| `SyncJumpWidth` | по справочнику CubeMX (обычно 1..4) | **Свободно**, часть битового тайминга. |
| `TimeSeg1` | по справочнику CubeMX | **Свободно**, часть битового тайминга. |
| `TimeSeg2` | по справочнику CubeMX | **Свободно**, часть битового тайминга. |

### Поведение контроллера

| Параметр | Допустимый диапазон | Что нужно библиотеке |
|---|---|---|
| `TimeTriggeredMode` | ENABLE / DISABLE | **Обязательно DISABLE.** Библиотека не использует Time Triggered Communication (временные метки SOF в кадрах) - не поддерживается и не ожидается нигде в коде. |
| `AutoBusOff` | ENABLE / DISABLE | **Свободно, работает в обоих случаях.** Библиотека сама программно восстанавливает периферию после Bus-Off (`HAL_CAN_Stop()`+`HAL_CAN_Start()` в `port_bus_off_recover()`) независимо от этой настройки - при `ENABLE` аппаратура и так восстановится сама, программный Stop+Start в этом случае избыточен, но не вредит. |
| `AutoWakeUp` | ENABLE / DISABLE | **Свободно, фактически не используется.** Библиотека не переводит периферию в Sleep и не ожидает автопробуждения. |
| `AutoRetransmission` | ENABLE / DISABLE | **Рекомендуется ENABLE** (это и есть NART-бит). При `DISABLE` - та же проблема, что в FDCAN выше: кадр, проигравший арбитраж или получивший ошибку, отменяется без повтора, `CANMGR_Send()`/`CANMGR_SendLatest()` всё равно вернут `HAL_OK`. Не блокирует инициализацию, только предупреждение `LOG_CODE_CANMGR_NO_AUTORETRANS`. |
| `ReceiveFifoLocked` | ENABLE / DISABLE | **Свободно.** Влияет только на поведение при переполнении RxFIFO (отбрасывать новый кадр или заменять последний принятый) - в обоих случаях событие попадёт в `HAL_CAN_ERROR_RX_FOV0` и будет учтено `CANMGR_GetRxOverflowCount()`/`LOG_CODE_CANMGR_RX_OVERFLOW`. Выбор зависит от того, что важнее в конкретном применении - не иметь значения для корректности самой библиотеки. |
| `TransmitFifoPriority` | ENABLE / DISABLE | **Обязательно DISABLE.** При `ENABLE` аппаратура выбирает, какой из нескольких занятых почтовых ящиков передать следующим, по приоритету ID, а не по порядку постановки - ломает тот же инвариант строгого FIFO, что и `TxFifoQueueMode = Queue mode` у FDCAN (см. выше), как только в аппаратных ящиках одновременно оказывается больше одного кадра. |

### Фильтры (банки)

Фильтры (вкладка "Filter" в CubeMX для bxCAN) конфигурируются библиотекой программно поверх
CubeMX-кода - `CANMGR_Init()` вызывает `HAL_CAN_ConfigFilter()` самостоятельно, с одним широким
фильтром (маска 0, пропускает все ID) на физический инстанс. Значения, выставленные на вкладке
"Filter" в CubeMX (`NumOfFilterBanks` и т.п.), **не имеют значения и библиотекой не читаются** - она
не использует код инициализации фильтров, сгенерированный CubeMX, полностью заменяя его своим.

На чипах с двумя физическими CAN (например STM32F407 - CAN1+CAN2, 28 банков на двоих) библиотека
сама назначает банки так, чтобы не нарушить физическую границу `SlaveStartFilterBank = 14` (банки
0..13 - CAN1, банки 14..27 - CAN2) - это зашито в код (`CANMGR_BXCAN_SLAVE_START_BANK`), трогать в
CubeMX ничего не нужно.

## Общее для обоих бэкендов - NVIC и запуск периферии

| Параметр | Что нужно библиотеке |
|---|---|
| Запуск периферии (`HAL_FDCAN_Start()`/`HAL_CAN_Start()`) | **Не вызывать из пользовательского кода** - библиотека сама стартует периферию внутри `CANMGR_Init()`. Двойной запуск не является ошибкой HAL, но нарушает ожидаемый порядок инициализации. |
| NVIC (FDCAN) | Включить прерывание приёма/ошибок/опустошения Tx (обычно единая линия `FDCANx_IT0` у большинства чипов - сверьтесь с распределением строк конкретного МК). |
| NVIC (bxCAN) | Включить `CANx_RX0_IRQn`, `CANx_TX_IRQn` и **обязательно** `CANx_SCE_IRQn` - без него события Bus-Off/переполнения Rx FIFO0 физически не дойдут до `HAL_CAN_ErrorCallback`, даже если нотификация активирована программно. |

## Коротко: минимальный чек-лист обязательных отклонений от умолчания CubeMX

Если бы CubeMX давал все параметры по умолчанию (как при создании нового проекта), для работы
библиотеки обязательно поменять:

- FDCAN: `FrameFormat = Classic CAN`, `StdFiltersNbr >= 1`, `ExtFiltersNbr >= 1`, `RxFifo0ElmtsNbr >= 1`,
  `TxFifoQueueElmtsNbr >= 1`, `TxFifoQueueMode = FIFO mode`, `RxFifo0ElmtSize`/`TxElmtSize = 8 bytes`.
- bxCAN: `TimeTriggeredMode = DISABLE`, `TransmitFifoPriority = DISABLE`.
- Оба бэкенда: `AutoRetransmission = ENABLE` (настоятельно рекомендуется, не блокируется библиотекой
  при отключении), периферию в CubeMX **не запускать**, NVIC - см. таблицу выше.

Остальные параметры (биты тайминга под нужный битрейт, Mode = Normal, прочие перечисленные выше как
"свободно") заполняются как обычно и на работу библиотеки не влияют.
